## 一、简历正文（可直接粘贴）

**企业级多租户 RAG 知识库问答系统** ｜ 个人项目 ｜ 2026.11
`Python` `FastAPI` `Pydantic` `Qwen3-Embedding/Reranker` `Milvus/Chroma` `Docling` `Docker` `Redis`

**项目描述**：面向 to B 知识库场景，构建覆盖「解析→切分→向量化→级联检索→重排→生成→溯源」全链路的 RAG 系统。核心解决三个工程问题：模型快速迭代下的**平滑升级**、海量租户的**配置与数据隔离**、检索无关内容导致的**LLM 幻觉**。

**核心工作（按设计决策组织）**：

- **设计可拔插的抽象契约层**：用 5 个 `Protocol`（Parser/Embedder/VectorStore/Reranker/LLM）+ 配置驱动工厂实现依赖倒置，第三方组件无需修改源码即可接入；业务代码零条件分支，切换实现仅改配置。为保障迁移正确性，将模型版本同时编码进 namespace 名与每条向量的 metadata，确保二者同源。

- **设计级联检索架构解决精度/速度矛盾**：双塔向量召回利用文档向量可离线预计算的特性实现海量快速筛选，交叉编码重排对 Top-K 做精排——针对"双塔有损压缩丢失词级交互、全库精排延迟不可接受"的权衡；重排分数与 cosine 不同量纲，独立重新排序；叠加相似度阈值与空结果短路，从数据源头阻断幻觉。

- **设计四层配置覆盖体系支撑多租户规模化**：全局→租户→文档类型→文档逐层覆盖且只存差异，由文档类型层吸收大部分定制，避免几万租户的配置表膨胀；`ResolvedConfig` 记录每个参数的来源层，支持配置问题快速定位。实现身份闸门与越权状态码映射（404/403/429）。

- **设计 Embedding 蓝绿迁移方案并完成真实模型替换**：建绿索引全量重建→增量双写→影子读质量验证→配置中心原子切流→保留回滚窗口，实现换模型不停机、可回滚。因切索引只换 namespace 而 embedder 是全局单例会导致"哈希 query 查 Qwen3 向量"的静默错误，设计模型-索引联动：namespace 编码 model_id，查询时反推并绑定对应 embedder，用 15 项测试固化该约束。本地真实接入 Qwen3-Embedding-0.6B 与 Qwen3-Reranker-0.6B，实测语义模型比哈希模型 top1 命中率高 25 个百分点，交叉编码器能把被误召回的相关文档从第二位救回第一。

- **把持久化做成可切换的后端而非写死实现**：租户存储抽出 `TenantStore` 协议（内存/PG 两实现），Registry 只保留校验与覆盖链逻辑，数据存取委托后端——换存储业务代码零改动；向量库同理可切 Chroma。用两个独立进程（A 写、B 全新连接读）验证"重启后数据还在"，避免同进程读写造成的假持久化。踩并修复三个 JSONB 真 bug（psycopg2 自动反序列化、list 被适配成 PG 数组、连接未关占用库）。

- **建立质量门禁并实测拦截有效**：GitHub Actions 跑编译→90 项测试→7/7 全链路→评测回归门禁（退化超容忍度直接 fail，绝不自动刷基线）。分支保护踩过"配了但拦不住"的坑：私有免费账号 rulesets 不强制、check 名用 job 的 name 而非 id 导致 required check 永不满足。改成公开仓库并让 check 名回落为 job id 后，用直推被拒 + PR blocked→clean 证明门禁真的生效。

- **扩展多模态能力**：将视频切分抽象为可拔插策略（固定窗口/场景边界优先），时间戳贯穿数据契约，支持基于时间段的溯源跳转。

**成果**：约 7800 行代码（app 层 4000+）、14 次提交、90 项测试全通过（另 5 项 PG 集成默认跳过）；提供 8 个可视化脚本与 DBeaver 直连文档，可观测每一步中间产物；真实质量对比报告见 `data/eval/model_migration_report.json`，生产化改进清单见 `docs/PRODUCTION.md`。

## 二、逐条讲解要点（面试官从哪句往下挖，你怎么答）

### 关于抽象契约层
- **为什么用 Protocol 而不是 ABC 抽象基类？** Protocol 是结构化子类型，实现类不需要显式继承——接入 Docling、Chroma 这类第三方库时不能改它们源码去继承我的类，Protocol 只要有同名方法就满足接口。ABC 要求继承，做不到这一点。
- **`@runtime_checkable` 的坑**：Protocol 默认不支持 `isinstance`，运行时检查会抛 TypeError，必须加装饰器。但它只查方法名存在，不校验签名——这个局限我知道。
- **工厂为什么要懒加载？** Docling/torch 这类重依赖体积大，原型档不该被拖垮。import 放在函数内部，只有真正切到那一档才加载。

### 关于级联检索
- **为什么两级？** 双塔文档向量可离线预计算、ANN 毫秒级，但把文本压成向量是有损压缩，丢失词级交互；交叉编码器能看到 query-doc 的注意力交叉项、精度高，但不能预计算、每个候选都要过一次模型。级联就是"便宜方法筛掉绝大多数，贵方法精挑少数"。
- **为什么分数不能混排？** cosine 在 -1~1，reranker 的 sigmoid 输出在 0~1，量纲不同，混排没有意义。我的实现是重排器输出后完全按新分数重新排序再取 top_n。

### 关于多租户配置覆盖
- **为什么分层？** 差异主要来自文档类型（视频按时间切、合同按条款切），放类型层能吸收大部分定制；只有少数大客户需要租户级定制。逐层只存 override，避免复制全套默认值。
- **为什么来源追踪重要？** 客户说"我调的参数没生效"，看 sources 字段就知道被哪一层覆盖了，排障成本大幅降低。

### 关于蓝绿迁移与真模型
- **为什么 namespace 名必须和 metadata 同源？** 我曾踩过一个真实 bug：namespace 用配置里的模型名生成，但实际 embedder 是哈希档，两个版本标记不一致，迁移时会误判该不该重建。改成用实际实例的 model_id 才同源。
- **切索引时为什么要同时切 embedder？** 这是真模型替换才暴露的问题：蓝索引存哈希向量、绿索引存 Qwen3 向量，查询若用旧 embedder 生成 query 向量，余弦相似度毫无意义且不会报错——是最危险的静默错误。我的方案是从 namespace 解析 model_id 反推 embedder，`make_search_fn` 里加防呆校验，不匹配直接抛错。
- **Reranker 踩过什么坑？** Qwen3-Reranker 是 `Qwen3ForCausalLM` 架构、没有分类头，用 `AutoModelForSequenceClassification` 加载会随机初始化分类头、打分全是噪音。我先手写 yes/no token 的 logit 发现打分反了，最后用 sentence-transformers 的 `CrossEncoder` 才对（相关 7.17 / 无关 -10.36）。
- **为什么 chunk 不用重切？** 切分只依赖文本，和 embedding 模型无关；只有从非语义切分换成语义切分时才需要重切。

### 关于持久化与验证方法
- **怎么证明数据真的落盘了？** 同进程写再读不算数——内存没清也能过。我用两个独立 Python 进程：进程 A 写入后退出，进程 B 全新连接读回。向量库验证的是"重启前后同一 query 的 top3 chunk id 逐位一致"，不是"top1 等于我预判的值"——后者是我一开始写错的断言。
- **为什么存储做成协议而不是直接调 PG？** Registry 里校验和四层覆盖链是核心业务逻辑，不该和存储耦合。抽出 `TenantStore` 协议后，内存版和 PG 版都实现同样三个方法，切换只改配置，业务逻辑一行没动。

### 关于 CI/CD 门禁
- **怎么知道门禁不是摆设？** 三件事验证：直推 main 被 ruleset 拒绝；开 PR 时 `mergeable_state=blocked`、CI 跑完 success 后变 `clean`；check 名必须和 ruleset 的 context 完全一致。GitHub 的 check 名优先取 job 的 `name` 字段，没有才用 job id——我给 job 起了中文 name 导致 required check 永不满足，PR 全卡死，删掉 name 才对齐。

### 关于诚实边界（被问到主动说）
> "原型档为了零依赖跑通链路用哈希 embedding 和抽取式 mock，这部分只验证控制流；真语义档我不是只写了代码——Qwen3-Embedding 和 Reranker 都真实下载、加载、跑过质量对比，top1 比哈希档高 25 个百分点，但这是 4 题的小样本教学演示，不是严格 benchmark。向量库默认内存不落盘，Chroma 持久化已实测重启恢复，Milvus 还是生产接口骨架；租户存储可切 PG 但默认仍是内存。我清楚每一档的边界，哪些补上就能上线、哪些只是接口就绪，我心里有数。"

## 三、这版为什么更像"工程项目"而不是 demo

| 维度 | demo 式写法 | 本版写法 |
|---|---|---|
| 叙事 | 我实现了 A、B、C | 我设计了 X 机制，解决 Y 矛盾，因为 Z |
| 深度 | 用了向量检索 | 双塔+交叉编码级联，因为有损压缩与预计算的权衡 |
| 可信 | 假装全用真模型 | 明确哪档跑过、哪档接口就绪、生产要补什么 |
| 规模感 | 几个测试文件 | 几万租户配置策略、蓝绿迁移不停机、可观测中间产物 |
| 反问能力 | 一追问就露馅 | 每个设计都有"为什么不用别的"的答案 |

**记住一句话**：面试官判定"项目深度"看的不是功能数量，是你能不能把每个设计决策的**约束—权衡—选择**讲清楚。这份文档就是训练这个能力。
