## 一、简历正文（可直接粘贴）

**企业级多租户 RAG 知识库问答系统** ｜ 个人项目 ｜ 2026.11
`Python` `FastAPI` `Pydantic` `Qwen3-Embedding/Reranker` `Milvus/Chroma` `Docling` `Docker` `Redis`

**项目描述**：面向 to B 知识库场景，构建覆盖「解析→切分→向量化→级联检索→重排→生成→溯源」全链路的 RAG 系统。核心解决三个工程问题：模型快速迭代下的**平滑升级**、海量租户的**配置与数据隔离**、检索无关内容导致的**LLM 幻觉**。

**核心工作（按设计决策组织）**：

- **设计可拔插的抽象契约层**：用 5 个 `Protocol`（Parser/Embedder/VectorStore/Reranker/LLM）+ 配置驱动工厂实现依赖倒置，第三方组件无需修改源码即可接入；业务代码零条件分支，切换实现仅改配置。为保障迁移正确性，将模型版本同时编码进 namespace 名与每条向量的 metadata，确保二者同源。

- **设计级联检索架构解决精度/速度矛盾**：双塔向量召回利用文档向量可离线预计算的特性实现海量快速筛选，交叉编码重排对 Top-K 做精排——针对"双塔有损压缩丢失词级交互、全库精排延迟不可接受"的权衡；重排分数与 cosine 不同量纲，独立重新排序；叠加相似度阈值与空结果短路，从数据源头阻断幻觉。

- **设计四层配置覆盖体系支撑多租户规模化**：全局→租户→文档类型→文档逐层覆盖且只存差异，由文档类型层吸收大部分定制，避免几万租户的配置表膨胀；`ResolvedConfig` 记录每个参数的来源层，支持配置问题快速定位。实现身份闸门与越权状态码映射（404/403/429）。

- **设计 Embedding 蓝绿迁移方案**：建绿索引全量重建→增量双写→影子读质量验证→配置中心原子切流→保留回滚窗口，实现换模型不停机、可回滚；namespace 版本化使新旧索引天然隔离。

- **扩展多模态能力**：将视频切分抽象为可拔插策略（固定窗口/场景边界优先），时间戳贯穿数据契约，支持基于时间段的溯源跳转。

**成果**：3800+ 行代码、9 次提交、32 项单元测试全通过；提供 8 个可视化脚本可观测每一步中间产物；配套生产化改进清单（异步流水线、混合检索、RAGAS 评测、K8s 部署方案），见 `docs/PRODUCTION.md`。

## 二、逐条讲解要点（面试官从哪句往下挖，你怎么答）

### 关于抽象契约层
- **为什么用 Protocol 而不是 ABC 抽象基类？** Protocol 是结构化子类型，实现类不需要显式继承——接入 Docling、Chroma 这类第三方库时不能改它们源码去继承我的类，Protocol 只要有同名方法就满足接口。ABC 要求继承，做不到这一点。
- **`@runtime_checkable` 的坑**：Protocol 默认不支持 `isinstance`，运行时检查会抛 TypeError，必须加装饰器。但它只查方法名存在，不校验签名——这个局限我知道。
- **工厂为什么要懒加载？** Docling/torch 这类重依赖体积大，原型档不该被拖垮。import 放在函数内部，只有真正切到那一档才加载。

### 关于级联检索
- **为什么两级？** 双塔文档向量可离线预计算、ANN 毫秒级，但把文本压成向量是有损压缩，丢失词级交互；交叉编码器能看到 query-doc 的注意力交叉项、精度高，但不能预计算、每个候选都要过一次模型。级联就是"便宜方法筛掉绝大多数，贵方法精挑少数"。
- **为什么分数不能混排？** cosine 在 -1~1，reranker 的 sigmoid 输出在 0~1，量纲不同，混排没有意义。我的实现是重排器输出后完全按新分数重新排序再取 top_n。

### 关于多租户配置覆盖
- **为什么分层？** 差异主要来自文档类型（视频按时间切、合同按条款切），放类型层能吸收大部分定制；只有少数大客户需要租户级定制。逐层只存 override，避免复制全套默认值。
- **为什么来源追踪重要？** 客户说"我调的参数没生效"，看 sources 字段就知道被哪一层覆盖了，排障成本大幅降低。

### 关于蓝绿迁移
- **为什么 namespace 名必须和 metadata 同源？** 我曾踩过一个真实 bug：namespace 用配置里的模型名生成，但实际 embedder 是哈希档，两个版本标记不一致，迁移时会误判该不该重建。改成用实际实例的 model_id 才同源。
- **为什么 chunk 不用重切？** 切分只依赖文本，和 embedding 模型无关；只有从非语义切分换成语义切分时才需要重切。

### 关于诚实边界（被问到主动说）
> "原型档为了零依赖跑通链路用了哈希 embedding 和抽取式 mock，这部分没有语义质量，只验证控制流；真语义档代码已实现（Qwen3），需要装 torch 切配置。向量库默认内存实现不落盘，Chroma 持久化可用，Milvus 是生产接口骨架。我清楚每一档的边界，也写了完整的生产化改进清单——哪些补上就能上线，我心里有数。"

## 三、这版为什么更像"工程项目"而不是 demo

| 维度 | demo 式写法 | 本版写法 |
|---|---|---|
| 叙事 | 我实现了 A、B、C | 我设计了 X 机制，解决 Y 矛盾，因为 Z |
| 深度 | 用了向量检索 | 双塔+交叉编码级联，因为有损压缩与预计算的权衡 |
| 可信 | 假装全用真模型 | 明确哪档跑过、哪档接口就绪、生产要补什么 |
| 规模感 | 几个测试文件 | 几万租户配置策略、蓝绿迁移不停机、可观测中间产物 |
| 反问能力 | 一追问就露馅 | 每个设计都有"为什么不用别的"的答案 |

**记住一句话**：面试官判定"项目深度"看的不是功能数量，是你能不能把每个设计决策的**约束—权衡—选择**讲清楚。这份文档就是训练这个能力。
