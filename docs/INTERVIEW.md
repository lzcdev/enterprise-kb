## 主题一：项目整体

### Q1.1 介绍一下这个项目

> **追问**：解决什么业务痛点？你在里面负责什么？有哪些技术难点？

**答**：这是一个面向企业 to B 场景的多租户知识库 RAG 问答系统，参考的产品形态是电商 SaaS 智能客服。它解决的问题是：企业有大量文档，客服回答问题时人工翻文档效率低，希望让 AI 基于知识库自动回答，而且答案要能溯源到原文。

我全程独立负责设计实现，从文档解析、切分、向量化、检索重排、到 LLM 生成和 API 服务，整条链路都是我自己搭的。技术难点主要有三个：第一是怎么让架构可平滑升级——因为模型迭代很快，我用了抽象接口加配置工厂，换模型只改配置不改业务代码；第二是怎么保证答案质量——做了双塔召回加交叉编码重排的级联，还有引用溯源和防幻觉闸门；第三是多租户——几万租户要数据隔离、配置差异化还不能让配置表爆炸。

项目最后 3800 多行代码，32 个测试全过，我还写了 8 个可视化脚本能演示每一步的中间产物。

### Q1.2 这个项目最难的地方是什么？

> **追问**：你是怎么解决的？有没有走弯路？

**答**：我觉得最难的是"既要能跑通验证、又要架构能平滑升级"这对矛盾。如果只用简单写法，很快能跑但换模型要推翻重来；如果一上来全用企业组件，本地装一堆重依赖根本跑不起来。

我的解法是抽象契约层加三档实现：定义 Parser、Embedder、VectorStore、Reranker、LLM 五个 Protocol，业务代码只依赖接口；然后做配置驱动的工厂，原型档用零依赖的确定性哈希和内存字典，生产档才用 Qwen3 真模型和 Milvus。这样原型档秒级跑通全链路、能写单元测试，升级到生产档只改配置。

走过弯路也说实话：中途发现 namespace 名用配置里的模型名生成，但实际 embedder 是哈希档，两个版本标记不一致，蓝绿迁移会误判——这是个真实的隐藏 bug，后来改成用实际 embedder 的 model_id 生成才同源。这让我意识到版本标记这种"小事"其实是迁移正确性的根基。

## 主题二：RAG 原理

### Q2.1 讲一下 RAG 的完整流程

> **追问**：离线和在线分别做什么？为什么这么拆？

**答**：RAG 分离线建库和在线查询两条线。

离线线是：加载文档 → 切分成 chunk → 每个 chunk 过 embedding 模型变成向量 → 存进向量库，同时把来源信息（文件名、页码）写进 metadata。这一步重、慢，但只做一次。

在线线是：用户问题过同一个 embedding 模型变成 query 向量 → 去向量库做相似搜索召回 Top-K → 可选的重排 → 把 Top-N 连同问题拼成 prompt → LLM 生成答案 → 解析答案里的引用编号生成溯源。

这么拆的核心是性能和成本的权衡：文档的向量表示不依赖具体查询，可以离线全量算好，线上只编码一次 query，才能做到毫秒级响应。如果在线才做文档编码，用户每次提问都要过全库，根本扛不住。

### Q2.2 换 embedding 模型要重新 chunk 吗？重新 embedding 吗？

> **追问**：换 LLM 呢？为什么？

**答**：换 embedding 模型必须全量重新 embedding，因为不同模型输出的向量不在同一个空间，新旧向量混在一个索引里相似度没有意义。但 chunk 一般不重切——切分是文本层面的，和 embedding 模型无关。除非你从非语义切分换成语义切分，那 chunks 的边界会变，才需要重切。

换 LLM 则完全不用动向量库，因为 LLM 只在生成那一步用，和前面检索的向量空间没有任何关系。

我项目里为此设计了蓝绿迁移：namespace 编码模型版本，换模型时建绿色 namespace 全量重建，双写追平后影子读验证质量，确认没问题再原子切流，旧索引保留一两周做回滚。

### Q2.3 为什么切分不能直接用固定长度？企业里怎么切？

> **追问**：需要大模型参与吗？表格怎么办？

**答**：固定长度切分会切断句子和语义，比如把一个完整条款从中间劈开，两半都失去意义。企业里主流是分层组合式切分：先用预解析提取标题、表格、代码这些结构，再按章节标题切成大块，块内用递归字符切分（按段落、句子、标点逐级降级）切到目标长度，每块还要把标题路径拼进去作为上下文，表格这种强结构要整块保留不能切。

需不需要大模型要看档位：常规的分层切分用规则就够，不用大模型，成本低速度快。但语义切分——就是按句子语义相似度找边界那种——要用 embedding 模型；还有用 LLM 做智能切分，成本高一般只在离线精加工时用。

表格绝对不能普通切，因为表格的语义在行列关系里，切开后行列错位，内容就废了。要么用 Docling 这类结构感知解析器整块提取，要么特殊保护整块保留。

## 主题三：检索与重排

### Q3.1 向量检索和 rerank 分别用了什么技术？

> **追问**：底层原理是什么？为什么有了向量检索还要 rerank？

**答**：这两个阶段用的都是深度模型，但都不是生成式 LLM。

向量检索底层是双塔 Bi-Encoder 加 ANN 索引。双塔就是 query 和文档各自过一个 embedding 编码器变成向量，文档向量可以离线全量算好存库，线上只编码 query，然后用余弦相似度找最近的。ANN 索引比如 HNSW 用多层图结构把暴力 O(n) 扫描降到近似 O(log n)。

rerank 底层是交叉编码器 Cross-Encoder，把 query 和 doc 拼成一条序列送进 Transformer，自注意力里有 query 对 doc 的交叉项，能捕捉词级对应、否定、数量关系，最后取 CLS 位置过分类头输出 0 到 1 的相关性分数。

为什么还要 rerank？因为双塔把文本各自压成一个向量，这是有损压缩，很多细粒度信息丢了。比如用户问"退款多久到账"，文档写"3-7 个工作日"，双塔可能因为没见过这种对应排得不高，交叉编码器让两者在注意力层直接交互就能看到这个对应。但交叉编码器慢、不能预计算文档表示，所以只能级联：向量检索先召回 Top10，rerank 再精排取 Top3。精度差来自压缩，速度差来自能否预计算——这是同一枚硬币的两面。

### Q3.2 粗召回和精排都用 LLM 了吗？

> **追问**：能全用纯算法吗？为什么不用 LLM 做 embedding？

**答**：都没有用生成式 LLM。业界说"大模型"特指自回归、能生成文本的模型，embedding 和 reranker 虽然也是神经网络，但参数量小得多、输出不是文本，所以不算 LLM。粗召回是深度模型加纯算法：embedding 生成表示是深度模型，余弦相似度和 ANN 索引是纯算法。精排是交叉编码器，一种 BERT 类深度模型。

技术上能不能全用纯算法？能，我项目原型档就是这么做的——embedding 用 md5 哈希，rerank 用 2-gram 关键词重叠率，零依赖跑通全链路。但这样完全没有语义理解，问"退款多久到账"匹配不到"3-7 个工作日"，检索质量很差，所以纯算法版只用来验证控制流和写单测，生产必须换专用模型。

为什么不用 LLM 做 embedding 或 rerank？可以但划不来。LLM 参数量几十亿到几百亿，编码一条文本的成本比专用小模型高一两个数量级；embedding 要处理全库文档、rerank 要对 Top10 每个候选打分，用 LLM 成本爆炸、延迟也扛不住。所以业界主流是专用小模型，比如 Qwen3-Embedding 0.6B，LLM 专注做最后生成。

### Q3.3 怎么防止检索到无关内容导致幻觉？

> **追问**：rerank 分数能和向量相似度一起排序吗？

**答**：我做了三道防线。第一道在检索层，设相似度阈值，低于阈值的结果直接丢弃——向量库总会返回 top_k 条，哪怕全不相关，不设阈值就会把无关内容喂给 LLM 硬答。第二道在控制流：如果阈值过滤后候选为空，我直接返回"知识库中没有相关信息"，根本不调用 LLM，因为空上下文喂进去它只能编。第三道在 prompt，明确要求只根据参考资料回答、资料没有就说不知道，并要求标引用。

rerank 分数和向量相似度绝对不能混排，量纲都不一样——cosine 是 -1 到 1，交叉编码器常是 sigmoid 后的 0 到 1。我的做法是重排器输出自己的分数后完全按新分数重新排序再取 top_n，绝不沿用粗召回的顺序。

## 主题四：多租户

### Q4.1 多租户的数据隔离你怎么做？

> **追问**：有哪几种隔离模式？大客户要求物理隔离怎么办？

**答**：隔离分三个强度档。最轻的是共享表加标签：所有租户数据在一个 collection 里，靠 tenant_id 的 metadata 过滤，成本最低但只是逻辑隔离。中等是分区：同一库内按租户分 namespace 或 partition_key，隔离性和成本折中。最强是独立库：每个租户一套独立 collection 或数据库实例，物理隔离、成本最高。

我项目原型档用的是第一种——共享索引加 tenant_id 过滤，查询强制带租户条件，实测跨租户零泄漏。架构上做了可升级：向量库实现抽象成接口，企业档可以切到 Milvus 的 partition_key 做分区，或者每租户独立 collection 做物理隔离，业务代码不用改。

### Q4.2 几万租户的配置怎么做？每租户一套参数吗？

> **追问**：为什么文档类型层最重要？

**答**：绝对不能每租户复制一套完整参数，几万租户会产生几万份重复配置，改个全局默认值要刷几万条。我的做法是四层覆盖链：全局默认、租户级、文档类型级、文档级，只存差异——租户配置里只写和默认不一样的那几个键，其余继承。

而且我把差异主要吸收到文档类型层。为什么？因为差异的来源主要是文档类型而不是租户：视频要按时间切、合同按条款切、扫描件要先 OCR，这些是类型共性，放类型层一个配置解决所有租户的同类文档。真正需要租户级定制的只是少数大客户，比如律所要求更细的切分。这样配置表就很小。

我还给解析结果加了来源标记，记录每个生效参数来自哪一层——客户说"我调的参数没生效"，一眼就能看出被哪层覆盖了。

### Q4.3 怎么防止租户越权访问？

> **追问**：只在查询时过滤够不够？

**答**：不够。只在查询时带 tenant_id 过滤是最后一道防线，但如果建库时标签贴错，或者有人绕过 API 直接查库，就泄漏了。我做的是纵深防御：身份识别 → 权限校验 → 数据过滤三层。

信任边界放在 API 层，外部 HTTP 请求是不可信输入，强制校验租户是否注册、是否被禁用，不同拒绝原因映射成不同状态码——未注册 404、已禁用 403、类型无权限 403、超配额 429。建库前还有前置校验：租户有没有权限传这个文档类型、文档数超没超配额。内部编排层则用软降级，因为请求已经被上层校验放行，不该因为查配置再把请求打挂。

## 主题五：工程化

### Q5.1 项目里哪些地方体现了可维护性？

> **追问**：为什么要抽象接口？有什么代价？

**答**：主要有三点。第一是抽象契约层：五个 Protocol 定义清楚每个组件的输入输出，业务代码只依赖接口不依赖具体实现，换实现只改工厂。第二是配置外置：用 pydantic-settings 从环境变量读配置，类型错了启动就报错，开发生产用不同 env 文件代码不改。第三是分层清晰：解析、切分、检索、重排、生成、服务各一层，每层能单独替换和测试，32 个测试就是分层带来的。

代价也要承认：抽象层会增加代码量和理解成本， Protocol 默认不支持 isinstance 还得加 `@runtime_checkable`，我在这踩了好几次坑。但对于需要频繁换模型的项目，这个代价是值得的——换 embedding 从"满项目找调用点"变成"改一个环境变量"。

### Q5.2 视频/音频是怎么接进来的？需要重新向量化吗？

> **追问**：视频怎么按场景切分？

**答**：多模态我是按契约演进的思路接的。不只是加一个 loader——先扩展数据契约：source_type 加 video/audio，元数据加 start_ms/end_ms 时间戳，否则 pydantic 校验直接拒绝视频数据。然后抽象三路提取接口：抽帧、音轨转写 Whisper、画面 OCR，时间轴对齐后聚合成带时间戳的 section。

要不要重新向量化看路线。路线 A 是把视频转成文本（VLM 描述加 ASR 台词加 OCR 文字）再做文本 embedding，这条路线向量空间不变，不用重做老数据，起步推荐。路线 B 是多模态模型直接编码视频，能和文字同空间检索，但换模型空间就变，要走蓝绿迁移全量重建。

场景切分是我特意做的：固定时间窗口会切断完整场景，我抽象了可拔插的切分策略，场景边界优先加时长约束——短于最小值的合并防碎片，长于最大值的均分防巨型块。固定窗口作为兜底策略保留，配置切换。

## 主题六：系统设计题

### Q6.1 让你设计一个企业知识库 RAG 系统，你怎么讲？

> **追问**：数据量很大怎么办？怎么保证答案质量？

**答**：我会分四层来讲。

第一层是在线服务层，FastAPI 提供问答接口，RAGService 编排检索到重排到生成的流水线，服务单例避免每请求重建模型。第二层是离线流水线层，文档解析、切分、向量化、建索引，这层重且慢，和在线解耦。第三层是能力层，就是那些可拔插的组件：解析器、embedding、向量库、重排器、LLM。第四层是存储层，向量库加原文存储，原文要支持回溯溯源。

数据量大的话，向量库从内存换成 Milvus 这种分布式向量库，用 ANN 索引加速；文档按租户分区；热门结果加缓存；在线楼层做水平扩展。切分参数按文档类型分层配置避免一刀切。

答案质量靠几个手段：双塔召回加交叉编码重排的级联提升相关性；相似度阈值和空结果短路防幻觉；引用溯源让答案可核对；还要有评测集持续回归——我项目里造了 10 条带标准答案的评测题，可以扩展成自动评测流水线。

多租户贯穿始终：数据隔离、四层配置覆盖、身份校验、配额控制。模型升级走蓝绿迁移保证平滑。

### Q6.2 如果让你把这个项目做得更像生产系统，还缺什么？

> **答**：我会诚实说几个明确缺的：第一是真模型的生产部署——本地原型档用的是确定性哈希，真语义档要部署 Qwen3 加 vLLM 或 TEI 服务；第二是向量库的持久化档真正接入和压测，目前 Chroma/Milvus 是骨架；第三是可观测性，完整的日志、链路追踪、指标监控；第四是评测体系，现在只有基础测试，需要 RAGAS 这类检索质量评测和线上反馈闭环；第五是权限体系细化，现在是租户 id 校验，真实系统要接 SSO/RBAC；第六是会话记忆和多轮对话，目前是单轮问答。我会说这些是我清楚知道边界、按优先级可以逐步补的，而不是假装项目已经完美。
