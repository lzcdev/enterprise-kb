# 评测集与回归门禁：AI 系统怎么做到"越改越好、不越改越差"

这是本项目从"教学原型"走向"可持续迭代工程"的关键一块。它回答一个问题：
**改完代码，怎么知道效果是变好了还是变坏了？**

## 一、为什么传统测试不够

pytest 那 62 项测试测的是**工程正确性**：JWT 防篡改、租户隔离、引用解析……都是确定性断言（`assert x == y`）。

但 RAG 的效果是**概率性、连续的**：同一问题换个 prompt，答案可能更流畅也可能开始编造。你没法写 `assert 答案 == "标准答案"`。所以必须建第二条轨道——**效果评测**。

## 二、本项目的评测设计（确定性近似，零依赖）

我们没有用 RAGAS / LLM 裁判（要 API key、有随机性、跑一次花钱），而是做了**可复现的确定性评测**——原型档也能建立基线。

### 评测集 `data/eval/golden.json`

12 条标注用例，覆盖 6 类场景（单文档定位 / FAQ / 表格 / DOCX / 无结构文本 / 无据拒答）。每条含：
- `question`：用户问题
- `relevant_source`：应命中的源文件（测检索）
- `key_facts`：答案必须出现的关键事实（测生成忠实度）
- `should_answer`：是否应该回答（无据问题应拒答）

### 指标（`app/eval/runner.py`）

| 指标 | 测什么 | 怎么算 |
|---|---|---|
| `recall@1/3/5` | 正确文档是否进 Top-K | 命中即 1，否则 0，取平均 |
| `mrr@10` | 正确文档排第几位 | 第一次命中排名倒数 1/rank |
| `faithfulness` | 答案是否含标准答案的关键事实 | 归一化字符串匹配 key_facts 命中比例 |
| `citation_hit_rate` | 溯源是否指向正确文档 | 引用列表含 relevant_source 即 1 |
| `abstention_accuracy` | 无据问题是否正确拒答 | 答案含"没有相关信息/未找到"即 1 |

**关键设计决策**：检索段用阈值 0.0（测纯排序能力），生成段用真实配置的阈值 0.3（测真实行为，拒答靠这道闸门）。两段分工不同，注释里写清了——这也是评测最容易踩的坑之一。

### 诚实边界

这些是 RAGAS 指标的**确定性近似**，不是语义 judge。当前原型档实测：

```
recall@3 = 0.90   faithfulness = 0.15   abstention = 1.00
```

**检索还行、生成质量很低**——因为哈希 embedding 无语义、MockLLM 是抽取式。这恰好证明评测有效：它如实暴露了"链路通但质量差"。切到 Qwen3 真模型后 faithfulness 应显著上升，这就是评测的价值。

## 三、回归门禁（`app/eval/gate.py`）

**核心：不看绝对分数，看相对基线是否退化。**

- 首次运行 `--save-baseline` 保存基线分数
- 之后每次评测对比基线，退化超过容忍度就 exit 1 阻断
- 容忍度按指标性质设：检索指标 0.10，生成指标 0.15
- **门禁绝不自动刷新基线**——否则"每次退化就把基线调低"等于没有门禁。刷新是一次显式决策。

已实测：把 faithfulness 基线临时抬到 0.6（当前 0.15），门禁 exit 1 并标出退化指标，恢复后 exit 0。

## 四、日常怎么用

```bash
# 一键本地验证（7 层：配置/解析/检索/生成/API/评测门禁/测试）
.venv/bin/python scripts/verify_local.py

# 首次建立基线
.venv/bin/python scripts/run_eval.py --save-baseline

# 日常/CI：评测 + 门禁（退化则 exit 1）
.venv/bin/python scripts/run_eval.py

# 看逐题明细（哪题没答对、召回了什么文档）
.venv/bin/python scripts/run_eval.py --verbose

# JSON 输出（CI 解析）
.venv/bin/python scripts/run_eval.py --json
```

产出的报告在 `data/eval/last_report.json`（每次跑都留档，可追溯质量趋势）。

## 五、接 CI/CD（下一步，本轮未做）

评测脚本已是 CI-friendly 设计（退出码 + JSON 输出），接 GitHub Actions 只需一个 workflow：

```yaml
- name: 评测门禁
  run: .venv/bin/python scripts/run_eval.py
```

门禁非 0 退出码自动让流水线失败。配合灰度/蓝绿发布，就是完整的"测→部署→盯指标→回滚"闭环。这部分留待下一步。

## 六、面试话术

> **问：RAG 项目怎么验证效果？和普通后端测试有什么不同？**
>
> "普通后端输出是确定的，写 assert 就行；RAG 输出是概率性的，没法写死期望值，所以要有第二条轨道——效果评测。我建了标注评测集，每条标了问题、应命中的文档、答案必须出现的关键事实。指标分两段：检索段测 Recall@k 和 MRR，生成段测忠实度和拒答准确率。关键是回归门禁：我不看绝对分数，而是保存基线，每次改动后重跑，退化超过容忍度就阻断合并。这样能持续迭代又不会越改越差。"
>
> **追问：为什么不用 RAGAS 这种成熟框架？**
>
> "生产上我一定会用 RAGAS 这类 LLM-judge 指标，更准。但这个项目是零依赖教学原型，我用确定性近似——关键事实字符串匹配、源文件命中判断——换来的是可复现、秒级、不用 API key，每次改动都能跑。指标接口设计成可替换的，评测集不变，把指标函数换成 RAGAS 就是生产版。我在文档里标清了这个边界，不会把近似指标当真语义 judge 讲。"
